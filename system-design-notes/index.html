Numbers Every 8+ YoE Engineer Must Know

⏱️ Latency Hierarchy (Orders of Magnitude)
  • L1 cache reference: ~ 0.5 - 1 ns
  • L2 cache reference: ~ 3 - 7 ns
  • Main Memory (RAM) access: ~ 100 ns
  • NVMe SSD random read: ~ 50 - 100 µs (1000x RAM)
  • Read 1 MB sequentially from RAM: ~ 3 µs
  • Read 1 MB sequentially from SSD: ~ 1 ms
  • Datacenter network roundtrip (RTT): ~ 0.5 ms
  • Intercontinental RTT (US ↔ EU): ~ 150 ms
📊 Back-of-Envelope Quick Multipliers
• 1 Day = 86,400 s ≈ 100K seconds (for quick mental math)
• 1 Million req/day ≈ 12 QPS | 100M req/day ≈ 1.2K QPS
• Peak Traffic multiplier: Design for 2x to 5x of average QPS!

Load Balancing Algorithms & Consistent Hashing

🔄
Round Robin / Weighted
Distributes sequentially. Weighted assigns higher traffic to bigger machines.
⚡
Least Connections
Routes to instance with fewest active connections. Best for long-lived sessions (WebSockets).
🎯
Consistent Hashing
Maps keys & nodes on a 360° ring with virtual nodes. Adding node remaps only K/N keys!
📍
Geo-Proximity
Routes users to the closest datacenter based on GeoDNS latency / BGP Anycast.

API Gateway Core Responsibilities & Rate Limiting Algorithms

🚪 API Gateway Pattern
  • Single Entry Point: Hides internal microservice topologies.
  • Authentication & JWT Validation: Offloads auth checks.
  • SSL / TLS Termination: Decrypts at perimeter; HTTP internally.
  • Protocol Translation: Translates HTTP/REST to internal gRPC.
  • Circuit Breaking: Fails fast on downstream service degradation.
🛡️ Rate Limiting Algorithms
1. Token Bucket Allows Bursts
Tokens added at fixed rate. Request consumes 1 token. If empty, HTTP 429 Too Many Requests.
2. Leaky Bucket Smooths Out Flow
Requests enter FIFO queue and processed at strictly constant rate. Drops excess requests.
3. Sliding Window Counter Accurate & Memory-Efficient
Weights previous window + current window: prev_count × (1 - weight) + curr_count.

Resilience: Circuit Breaker State Machine

🟢 CLOSED (Normal)
All requests pass through.
Failures counted over rolling time window.
If failures > Threshold (e.g. 50%) →
🟡 HALF-OPEN (Testing)
Allows canary sample requests.
If success → CLOSED
If failure → OPEN
← Timeout expires (e.g. 30s)
🔴 OPEN (Tripped)
Fails immediately (Fast-Fail) or returns fallback cache response. Protects downstream service!

Sketches: the Hash Ring & the Token Bucket

🧮 Why virtual nodes?

  • 3 physical nodes = 3 uneven arcs → hot spots
  • 100–300 vnodes each → arcs average out (±5–10%)
  • Bigger machine? give it more vnodes

⚙️ Distributed limiter

  • Key: `rl:{userId}:{endpoint}` in Redis
  • Lua script = read + refill + decrement atomically
  • Return `X-RateLimit-Remaining` + `Retry-After`
⭐ Golden Rule for Consistent Hashing
✓ Standard hash (hash(key) % N) causes 99% cache misses when cluster size $N$ changes! Consistent hashing with Virtual Nodes (100-300 per physical server) prevents Hotspots and ensures uniform load distribution.
💡 Staff / Senior Interview Tip
Q: How do you prevent Thundering Herd on cache invalidation or server restart?
A: Use Mutex / Singleflight locks (only 1 thread fetches from DB while others wait), Probabilistic Early Expiration (XFetch algorithm), and Randomized TTL Jitter so millions of cached keys don't expire simultaneously at the top of the hour.

Distributed Caching & Invalidation Strategies

①

4 Core Caching Patterns (Where & How Writes Occur)

📖
Cache-Aside (Lazy)
• App reads Cache first.
• If Miss → Read DB → Write to Cache.
✓ Only caches requested data.
✗ Cache misses have 3x latency.
✍️
Write-Through
• App writes to Cache.
• Cache synchronously writes to DB.
✓ High data consistency.
✗ Higher write latency.
⚡
Write-Back (Behind)
• App writes to Cache immediately.
• Cache async flushes to DB in batches.
✓ Extreme write throughput.
✗ Data loss risk if cache dies.
🔄
Write-Around
• App writes directly to DB.
• Bypasses Cache completely.
✓ Prevents cache pollution.
✗ Fresh writes trigger cache miss.
②

Cache Production Pitfalls & Battle-Tested Fixes

🌊 Cache Avalanche
Problem: Massive number of keys expire at the exact same second, causing DB CPU to spike to 100%.

Solution:
• Add Random TTL Jitter (TTL = base_ttl + rand(1, 300)s).
• Multi-region distributed cache deployment.
🕳️ Cache Penetration
Problem: Attackers query non-existent keys (e.g. user_id = -999). Misses bypass cache and hit DB directly.

Solution:
• Bloom Filter in front of Cache (O(1) space/time to check existence).
• Cache empty/null results with short TTL (60s).
💥 Cache Breakdown / Stampede
Problem: A single viral "hot key" (e.g. World Cup score) expires; 50,000 concurrent threads hit DB.

Solution:
• Distributed Mutex (Redis SETNX): only 1 worker regenerates cache.
• Background async pre-warm cron job.

Redis vs Memcached

VS
Redis
Data Types: Strings, Hashes, Lists, Sets, Sorted Sets (ZSET), Bitmaps, HyperLogLog, Streams
Threading: Single-threaded event loop (I/O multiplexing epoll) + Multi-threaded I/O in v6+
Persistence: RDB snapshots + AOF write log
Replication: Native Master-Replica + Sentinel + Cluster (16,384 Hash Slots)
Memcached
Data Types: Pure Key-Value byte strings only
Threading: True Multi-threaded architecture (scales linearly with CPU cores)
Persistence: None (Pure in-memory, volatile)
Replication: No native clustering (client-side consistent hashing required)

Cache Eviction Algorithms

🗑️ Eviction Policy Cheatsheet
  • LRU (Least Recently Used): Evicts keys not read for the longest time. (Standard choice; implemented via Doubly Linked List + Hash Map in O(1)).
  • LFU (Least Frequently Used): Tracks access counters. Evicts least popular items. Great for static catalog access.
  • FIFO: First-In-First-Out queue order. Simple but suboptimal.
  • 2Q / ARC (Adaptive Replacement Cache): Balances recency and frequency dynamically.
⑤

Cache-Aside, Step by Step (sequence sketch)

📈 Hit-ratio math

  • avg latency = h·0.5ms + (1 − h)·10ms
  • h = 0.90 → 1.45 ms · h = 0.99 → 0.6 ms
  • Every extra "9" of hit-rate ≈ halves DB load

🔑 Key hygiene

  • Namespaced + versioned: `v2:user:42`
  • Bump the version to invalidate a whole schema
  • Keep values small (< 100 KB) — big values block Redis' single thread

🧊 What NOT to cache

  • Balances / inventory used for a decision
  • Data with a 1:1 read:write ratio
  • Anything you can't afford to be stale
⭐ Dual-Write Problem: Invalidate vs Update
✓ Never update cache directly on DB write due to race conditions (e.g. Thread A writes DB, Thread B writes DB, Thread B updates Cache, Thread A updates Cache $\to$ Stale Cache!).
✓ Standard Pattern: Write to DB first $\to$ Delete (Invalidate) from Cache.
💡 Staff / Senior Interview Tip
Q: How do you achieve 100% cache-DB consistency without race conditions?
A: Use Change Data Capture (CDC via Debezium) connected to the Database Write-Ahead Log (WAL). DB commits the transaction $\to$ Debezium publishes change to Kafka $\to$ Dedicated consumer service invalidates Redis cache asynchronously with retry guarantees.

CAP Theorem & The Realistic PACELC Theorem

🔺 CAP Theorem (Pick Any 2 during network partition)
  • Consistency (C): Every read receives the most recent write or an error.
  • Availability (A): Every non-failing node returns a non-error response (without guarantee of latest data).
  • Partition Tolerance (P): System continues operating despite network drops between nodes. (Mandatory in distributed systems!).
  • CP Systems: Google Spanner, HBase, ZooKeeper.
  • AP Systems: Apache Cassandra, CouchDB, DynamoDB.
⚖️ PACELC Theorem (Extended Real-World Model)
If there is a Partition (P), trade off Availability (A) vs Consistency (C);
Else (E) (normal operation), trade off Latency (L) vs Consistency (C).

• PA/EL: Cassandra, DynamoDB (Low latency favored over strong consistency in normal state).
• PC/EC: Google Spanner, CockroachDB (Strong consistency always prioritized).
③

Database Sharding Strategies & Challenges

1. Range-Based Sharding
Sharded by key ranges (e.g. Users A-D on Shard 1, E-H on Shard 2).
✓ Range queries easy.
✗ Hotspot risk (Celebrity 'J' overloads Shard 3).
2. Hash-Based Sharding
Shard = hash(user_id) % N.
✓ Uniform data distribution.
✗ Range queries require scatter-gather across all shards.
3. Directory / Lookup-Based
Lookup service maps partition key to shard ID.
✓ Flexible dynamic re-sharding.
✗ Lookup service is single point of failure / latency hop.

⭐ Storage Engine Tradeoff: B-Tree vs LSM-Tree
✓ B+ Tree (Postgres/MySQL): In-place updates, faster reads (O(log N)), higher write amplification.

Q: How do you handle Cross-Shard Transactions without blocking the entire database?
A: Avoid distributed 2-Phase Commit (2PC) in high-throughput systems because coordinator locks cause high tail latency. Instead, co-locate related records using a shared Composite Partition Key (e.g., tenant_id:user_id), or use an asynchronous Saga Orchestration Pattern.

Distributed Transactions: Outbox Pattern & Sagas

📦 Transactional Outbox Pattern
Problem: Updating DB and publishing to Kafka is NOT atomic (one can fail).

Solution Flow:
1. App saves business entity + message into outbox_table in the same local DB transaction.
2. CDC engine (Debezium) reads DB WAL log and publishes to Kafka.
✓ 100% atomic dual-write guarantee without distributed locks.
🎭 Saga Pattern for Distributed Workflows
Replaces slow blocking Two-Phase Commit (2PC) across microservices:

• Choreography: Services listen to domain events and execute local transactions independently.
• Orchestration: Central orchestrator (Temporal / AWS Step Functions) coordinates workflow.
• On failure, executes explicit Compensating Transactions (e.g. Refund Payment).
④

Picture Kafka: Partitions, Offsets & Consumer Groups

📏 Sizing partitions

  • #partitions ≥ peak MB/s ÷ per-consumer MB/s
  • Over-provision a bit — increasing later reshuffles key → partition

🔥 Hot partition

  • One celebrity key = one overloaded partition
  • Fix: salt the key (`key#0..N`) when ordering isn't needed

📉 Watch consumer lag

  • lag = latest offset − committed offset
  • Rising lag = scale consumers or speed up handlers
⭐ Kafka Partitioning Law
✓ In Kafka, 1 partition can only be read by 1 consumer thread in a consumer group at any time! To scale consumer throughput, you must increase the number of partitions. Setting partition key = user_id guarantees all events for that user arrive in exact chronological order.
💡 Staff / Senior Interview Tip
Q: How do you prevent Poison Pill messages from blocking an entire Kafka partition?
A: Implement a Dead Letter Queue (DLQ) with Exponential Backoff + Jitter. On message deserialization or unrecoverable error, write the payload + stack trace to a order-events-dlq topic after $N$ retry attempts, alert on-call, and commit the partition offset so valid customer messages continue processing.

Storage Systems, CDNs & Media Pipelines

①

Storage Types: Block vs File vs Object Storage

🧱
Block Storage (EBS, SAN)
• Raw disk blocks without metadata.
• Ultra-low latency IOPS.
• Attached to single instance.
Best for: Databases, OS boot disks.
📁
File Storage (EFS, NFS)
• Hierarchical folder structure.
• Shared across multiple servers.
• POSIX compliant file locks.
Best for: Shared configs, Legacy apps.
🪣
Object Storage (S3, GCS)
• Flat namespace with metadata.
• Immutable files accessed via HTTP API.
• 99.999999999% (11 9's) durability.
Best for: Videos, Images, Backups.
②

Content Delivery Networks (CDN): Push vs Pull

VS
Pull CDN (Origin Fetch - Default)
Workflow: Edge PoP fetches content from Origin server on first user request (Cache Miss), then caches it for TTL.
Storage Cost: Minimal (only popular cached assets stored at edge)
Maintenance: Zero origin management; automatic eviction.
Best For: High-traffic web apps, blogs, YouTube thumbnails.
Push CDN (Proactive Upload)
Workflow: Origin server pushes all new/updated content to edge servers proactively prior to user requests.
Storage Cost: Higher (all assets distributed to all edge locations).
Latency: 0ms origin miss latency for all users.
Best For: Large software updates (iOS updates, game patches).
③

Large Video / File Upload Pipeline (e.g. YouTube, Google Drive)

1. Client requests upload signature from API Pre-Signed S3 URL (5-min expiry)
↓ Direct Client-to-S3 bypasses API Servers
2. Client uploads file in 5MB chunks in parallel S3 Multipart Upload / TUS Protocol
↓ S3 Object Created Event Trigger
3. S3 triggers SNS/SQS Transcoding Queue Event-Driven Pipeline
↓ Distributed Worker Cluster (FFmpeg on GPU)
4. Workers encode video into HLS / DASH (1080p, 720p, 480p) HLS .m3u8 manifests + .ts segments
④

The Upload → Transcode → Stream Pipeline (sketch)

🧾 Cache-Control cheat

  • Video chunks / hashed assets: `public, max-age=31536000, immutable`
  • Manifests (.m3u8): short TTL, e.g. `max-age=10`
  • Private content: signed URL + `private`

♻️ Resumable uploads

  • Split into 5–100 MB parts, upload in parallel
  • Retry only the failed part; complete with ETag list
⭐ Never Stream Large Files Through App Servers!
✓ Streaming 2GB video uploads through your API Gateway / Node.js servers exhausts thread pools and network bandwidth immediately! Always generate an Amazon S3 Pre-Signed Upload URL or use the TUS open resumable upload protocol for direct client-to-storage transfers.
💡 Staff / Senior Interview Tip
Q: How do you search across billions of text records in sub-50ms?
A: Use an Inverted Index (Elasticsearch / OpenSearch). Unlike relational DBs that scan rows, an inverted index maps every unique word/token to a sorted list of Document IDs (Posting List). Combining multiple terms uses fast bitwise AND / OR operations across posting lists.

Distributed Consensus, Coordination & ID Gen

①

Consistency Models Spectrum (Strongest to Weakest)

🔒
1. Linearizable (Strict)
• 1. Linearizable (Strict)
All operations appear instantaneous on a global real-time clock. Total global order.
⚡
2. Sequential
• 2. Sequential
All operations seen in the same order by all nodes; may lag real physical clock.
👤
3. Read-Your-Own-Writes
• 3. Read-Your-Own-Writes
A user always sees their own updates immediately. Other users see it eventually.
🌊
4. Eventual Consistency
• 4. Eventual Consistency
If no new updates, all replicas eventually converge to identical state.
②

Consensus (Raft Algorithm)

🗳️ Raft Core Mechanics (etcd, Consul)
  • Leader Election: Randomized election timers (150-300ms) prevent split-vote deadlocks.
  • Quorum Rule: Requires majority vote (Q = ⌊N/2⌋ + 1). A 5-node cluster survives 2 node failures.
  • Log Replication: Leader appends entry → replicates to followers → commits once majority ACKs.
  • Split-Brain Proof: Only 1 partition can have a majority quorum.
③

Distributed Locks & Fencing Tokens

⚠️ The Dangerous Distributed Lock Trap
Client 1 acquires lock → JVM triggers Full GC pause for 15s → Lock TTL expires → Client 2 acquires lock → Client 1 wakes up and writes to DB → Data Corruption!

Mandatory Fix: Fencing Tokens
Lock service issues monotonically increasing token (e.g. 33, 34, 35). Storage engine rejects writes with token < current highest token.

Sketches: a Raft Quorum & Why Locks Need Fencing Tokens

🧠 Quorum rule: with N replicas, write quorum W and read quorum R, you read your latest write when W + R > N (e.g. N = 3, W = 2, R = 2). Cassandra/Dynamo let you tune it per query.
⭐ NTP Clock Drift is Real
✓ Physical server clocks drift via NTP adjustments or leap seconds. Never rely on wall-clock time for strict distributed ordering. Use Logical Clocks (Lamport Timestamps / Vector Clocks) or hardware atomic clocks with bounded uncertainty intervals (Google Spanner TrueTime API).
💡 Staff / Senior Interview Tip
Q: Why is Redis Redlock controversial for distributed locking?
A: Distributed systems expert Martin Kleppmann showed that Redlock relies on synchrony assumptions (bounded network delays and monotonic physical clocks). If a process experiences an unpredicted GC pause or VM migration, Redlock can grant two clients the lock simultaneously. For safety-critical state, always use etcd / ZooKeeper linearizable sessions with fencing tokens.

Case Study: Design a URL Shortener (TinyURL)

✎ A full 45-minute answer, written the way you'd talk through it. Follow the numbered rail.
①

Scope It (5 min)

✅ Functional
  • Shorten a long URL → 7-char code
  • Redirect `GET /{code}` → long URL
  • Optional custom alias & expiry
  • Click analytics (async, can lag)
📏 Non-functional & napkin math
  • 100M new URLs / month ≈ 40 writes/s
  • Read:write = 100:1 ⇒ ~4K redirects/s, peak ~20K
  • 5 yrs × 1.2B/yr × 500 B ≈ 3 TB
  • 62⁷ ≈ 3.5 trillion codes — plenty
  • p99 redirect < 50 ms · 99.99% available

↪️ 301 or 302?

  • 301 permanent: browser caches it → fewer hits, but you lose analytics
  • 302 temporary: every click reaches you → accurate stats ✅

🛡️ Abuse & safety

  • Rate-limit creates per user / IP
  • Scan targets against malware lists (async)
  • Shuffle the id → code mapping so codes aren't sequential

⏳ Expiry

  • Check `expires_at` on read (lazy)
  • Nightly sweeper deletes rows (or native TTL in DynamoDB/Cassandra)
⭐ Trade-offs to Say Out Loud
✓ Cache-aside with long TTL is safe here because mappings are immutable.
✓ Eventual consistency is fine for analytics, not for code uniqueness — that's why KGS owns id ranges.
✓ Custom aliases go through a conditional write (`PutItem if not exists`) to avoid races.
💡 Staff-Level Follow-up
Q: A link goes viral — 1M redirects/s for one code. What breaks?
A: One Redis shard becomes hot. Add an in-process LRU cache (seconds-long TTL) on every redirect pod, and serve the 302 from the CDN edge with a short `max-age`, so the origin sees a trickle instead of the flood.

①

Scope It

✅ Functional

Deep Dives

🔢 Ordering

  • Order per conversation, not globally
  • Kafka key = conv_id → one partition per chat
  • Server assigns msg_id; clients sort by it, never by device clock

👥 Group fanout

  • Small groups: write once, fan out to each member's inbox/socket
  • Huge channels (Slack): members pull since their last-read cursor

📲 Multi-device sync

  • Each device keeps `lastSeenMsgId` per chat
  • On reconnect: fetch `msg_id > cursor` from Cassandra

🔌 Gateway dies?

  • Clients reconnect with jittered backoff to any gateway
  • Registry entry has a TTL, so stale routes expire
  • Nothing lost: messages were persisted before ✓
⭐ Why Cassandra for Messages?
✓ Write-heavy (200K/s) append-only workload → LSM-tree storage shines.
✓ Access pattern is always "latest N messages of conversation X" → partition by `(conv_id, month_bucket)`, cluster by `msg_id DESC`.
✓ The bucket keeps partitions from growing forever in long-lived chats.
💡 Staff-Level Follow-up
Q: How would you add end-to-end encryption?
A: Clients exchange keys (Signal protocol: identity + pre-keys published to a key server); the server only relays ciphertext. Consequences: no server-side search, group messages are encrypted per member (or via sender keys), and push notifications carry only a "you have a message" hint.
